# 常駐代理（Super-agent）：與 xHarness 的比較及整合規劃

2026-11-02 草案。

比較對象：
- DeepSeek 的文章〈Super-agent 設計探索：邁向更自主的 Agent 系統〉
- 文章附的公開原型 [deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)（MIT 授權，2026-10-31 釋出，附 9 份設計文件）

xHarness 以 `feat/multiagent` 分支（1.18.0，PR #3）為準。

---

# 第一部分：比較

## 1. 兩邊各是什麼

| | 原型 dsh-superagent | xHarness |
|---|---|---|
| 形態 | DeepSeek Harness 的外掛，專做「一個 GitHub 存放庫的主動寫程式代理」 | 通用的 agent harness：命令列、網頁、桌面版、Telegram，可多節點 |
| 程式 | TypeScript，連測試約 25,000 行，60 個測試檔 | Python 標準函式庫、零相依，約 20,000 行，578 個測試 |
| 誰開始一件工作 | 事件：GitHub 通知、飛書訊息、CI 結果 | 人：開一段對話下指令（Telegram 一對一也是對話） |
| 設計原則 | 「花最少的人的注意力，給最多價值」：只在被要求或規則允許時動手，只在要人決定或有結果時開口 | 「管得住的代理」：審批、沙箱、煞車、稽核優先，給政府與學校交付 |

一句話：原型強在「代理自己接事件、分派、跟進」，xHarness 強在「代理做事時管得住、查得到」。兩邊幾乎互補。

## 2. 逐項比較

判定欄：**有**＝xHarness 已有同等能力；**部分**＝有雛形；**沒有**＝要新做；**我們較強**＝xHarness 做得比原型多；**不做**＝刻意不跟。

### 驅動與事件

| 項目 | 原型 | xHarness 現況 | 判定 |
|---|---|---|---|
| 事件來源 | GitHub（通知、指定的 issue 與 PR、CI 變化、PR 合併關閉）、飛書 | Telegram 一對一、`/api/notify` 推播、對話內提醒（要開著網頁才會觸發） | 沒有 |
| 事件模型 | Trigger 一筆事件、Thread 同一串、Correlation 只補上下文不改路由 | 無 | 沒有 |
| 重啟不重播 | 每個來源記住讀到哪裡；同一事件接兩次只開一張工單 | 無 | 沒有 |
| 批次合併 | 同一線程一次只跑一個評估，期間進來的事件併到下一批 | `agentcomm` 收件匣下一輪才讀，只用在代理之間 | 部分 |

### 准入與授權

| 項目 | 原型 | xHarness 現況 | 判定 |
|---|---|---|---|
| 程式規則先篩 | 名單、有沒有點名代理、准入表（三格：名單內未點名／名單外點名／名單外未點名）、機器人名單 | 模型路由用的是同一種寫法：程式硬規則先、模型後（`router.py`） | 部分（寫法可直接沿用） |
| 模型判斷主動工作 | 團隊用文字寫規則，模型每條都要表態；至少一條符合才能主動接 | 無 | 沒有 |
| 接單模式 | off／observe（預設，只記錄「本來會接」）／auto | 無 | 沒有 |
| 授權寫死在工單上 | Mandate：範圍、強度（明確／推斷）、依據的規則與政策版本；訊息內容改不了 | 無；授權只有「工具呼叫要不要核准」這一層 | 沒有 |
| 規則改版 | 規則有版本；改規則不砍進行中的工作，而是通知它，接續前再驗一次 | 無 | 沒有 |
| 使用者身分 | 每個來源各自的帳號 ID，不跨來源對應 | 帳號、角色、LDAP、配額 | 我們較強（但要補「來源帳號」這一層） |

### 分派

| 項目 | 原型 | xHarness 現況 | 判定 |
|---|---|---|---|
| 常駐主會話 | 一個常駐會話只分派、不做事，工具只有 14 個路由用的 | 無；主代理自己決定要不要叫子代理 | 沒有 |
| 委派穩不穩 | 架構保證交出去 | 靠提示詞。文章實驗：中性提示下 5 次都沒委派，P95 要 29.5 分鐘 | 沒有（這是要做的主要理由） |
| 訂閱直通 | 工單訂閱線程，後續事件直接送到工作代理，不經主會話；多對多 | 無 | 沒有 |
| 交回與改派 | 工作代理可說「這則不是我的」交回主會話 | 無 | 沒有 |

### 執行

| 項目 | 原型 | xHarness 現況 | 判定 |
|---|---|---|---|
| 每件工作的隔離 | 每張工單一個會話、一個目錄，用 prepare 指令建 git worktree | 子代理各自的 git worktree，從工作目錄快照建立 | 有 |
| 改動套回前的檢查 | 無；工作代理自己開 PR | 整合關卡：系統執行檢查指令，通過且能乾淨套用才套回；失敗就留成分支 | 我們較強 |
| 工作代理的權限 | **不經核准**，以作業系統使用者身分直接跑指令 | 審批（prompt／auto）、bwrap 沙箱、token 煞車、每人配額 | 我們較強 |
| 驗證結果 | 工作代理回報 | 任務板的驗證紀錄分「系統驗證過」和「代理自稱」 | 我們較強 |
| 長指令不卡對話 | 5 秒自動轉背景；做完叫醒工作代理 | `job_start` 與背景子代理都有，但做完要等人下一則訊息才通知 | 部分 |
| 並行槽位 | 有上限，另外保留一格給人的訊息，新工作擋不住人的跟進 | 子代理有並行上限，沒有保留給人的那一格 | 部分 |

### 回覆與管道

| 項目 | 原型 | xHarness 現況 | 判定 |
|---|---|---|---|
| 回到原來的地方 | 在哪裡被叫就回哪裡：飛書話題、GitHub 留言、審查討論串 | Telegram 一對一可回；LINE、Teams 只能送通知 | 部分 |
| 依管道調整寫法 | IM 一次不超過 100 詞、GitHub 用結構化 PR 說明 | Telegram 有專用提示詞，沒有長度上限 | 部分 |
| 對外寫入要不要人點頭 | 不用 | 工具呼叫可以送到手機核准 | 我們較強（要延伸到寫回） |
| 寄送保證 | outbox：每則訊息有編號、不會送兩次；失敗以 2 秒起倍增重試，最長 1 分鐘 | 通知送失敗就算了，沒有重送佇列 | 沒有 |

### 可靠性與維運

| 項目 | 原型 | xHarness 現況 | 判定 |
|---|---|---|---|
| 先記錄再執行 | 決定之後的動作（派工、轉送、寫回）先存進佇列再做 | 無 | 沒有 |
| 重啟復原 | 進行中的派工以「主機重啟」結束，新派工附復原說明：先查目錄、git、GitHub，避免重複對外動作 | 對話紀錄可接續；systemd 會自動重啟 | 部分 |
| Watchdog | 文章：獨立會話定時檢查，含模型判斷有沒有實質進展；原型：每小時檢查 | 無 | 沒有 |
| 設定與提示詞版本 | 每次存檔有版本與歷史 | 設定檔是 TOML；通知頻道可在網頁管理 | 部分 |
| 安裝 | 由寫程式的代理照 SETUP.md 一問一答裝 | 有安裝包、`docs/deployment-school.zh.md` | 有 |

### 介面

| 項目 | 原型 | xHarness 現況 | 判定 |
|---|---|---|---|
| 主畫面 | 概覽／來源／觸發／評估／執行／設定，只先列要人處理的 | 對話、艦隊看板、資安檢查頁、通知頻道設定 | 部分 |
| 每則事件的去向 | 可查：被篩掉、評估結果、送到哪張工單、被誰交回 | 無 | 沒有 |

### 治理與交付（xHarness 獨有）

這些原型都沒有：
- 稽核紀錄與服務使用報告（Word 月報）
- SSDLC 證據包、資安檢查頁
- 機密以 AES-256-GCM 加密存放
- 模型路由硬規則：來源國限制、外購模型不看本機資料
- 多節點艦隊、手機核准
- 地端評測、討論引擎的確定性查核

原型在這塊只寫了一段「Responsibility」，請操作者自己負責。

文章 8.4 節承認兩件事還沒解：事件會帶進不可信的輸入、憑證會進到模型的上下文。這正好是 xHarness 的強項。

# 第二部分：整合規劃

## 4. 目標

在 xHarness 節點上常駐一個代理：
- 它自己聽 GitHub 與 Telegram 群組的事件，先用程式規則篩，再由模型判斷。
- 接下來的工作開成工單，交給各自隔離的工作代理去做，結果回到原本的話題或 PR。
- 人只在要決定、要驗收時被叫。

xHarness 原有的審批、沙箱、整合關卡、稽核一個都不放鬆。

## 5. 架構

```
來源（GitHub 輪詢、Telegram 群組）
   │ 觸發，寫入 superagent.db，記住讀取位置
   ▼
准入（程式規則：名單、點名、准入表、機器人名單）── 不准 → 只記錄去向
   │ 准
   ├─ 已有工單訂閱這條線程 → 直通給該工單（不經主會話）
   ▼
主會話（常駐、只分派不做事、granite）
   │ 一批批處理：接單／併入／停止／忽略
   ▼
工單 → 一段工作對話（自己的 worktree、沙箱、核准規則照舊、整合關卡）
   │ 回報：進展／等人／待驗收／卡住／失敗
   ▼
outbox → 管道寫回（GitHub 留言或 PR、Telegram 回覆），預設每筆過手機核准
```

Watchdog 在旁邊定時檢查：
- 工單多久沒有實質進展
- 是否反覆呼叫同一個工具
- 來源是否斷線
- 佇列是否卡住

有異常就推到手機。

## 6. 模組

| 檔案 | 內容 |
|---|---|
| `xharness/superagent.py` | 資料層。SQLite（`$XHARNESS_HOME/superagent.db`）存：來源讀取位置、觸發、去向、線程、訂閱、工單、派工、決定、動作佇列、outbox。寫法沿用 `board.py`（用 `BEGIN IMMEDIATE` 防重複接單） |
| `xharness/sources.py` | 來源介面與登錄。`GitHubSource`：notifications API 輪詢、PR 與 CI 狀態，不需要公開網址。`TelegramGroupSource`：掛在現有 `telegram.py` 的輪詢上 |
| `xharness/admission.py` | 准入：名單、准入表、機器人名單、接單模式、規則與政策版本 |
| `xharness/orchestrator.py` | 主會話與它的工具：`route`、`read`、`reply`、`eval_decide`、`ticket_retry`、`requeue`；觸發的批次合併。只給路由用的工具，不給 bash |
| `xharness/tickets.py` | 工單生命週期與階段排序；派工時呼叫 `WebApp.create` 開一段工作對話，帶 `isolate`，網頁與艦隊看板看得到。工作代理的工具：`ack`、`report`、`thread_follow`、`thread_unrelated`、`handback` |
| `xharness/channels.py`（改） | 加寫回端：GitHub 留言、開 PR、Telegram 群組回覆。走 outbox，不會送兩次、失敗退避重試；寫入前核准，結果寫稽核 |
| `xharness/watchdog.py` | 定時檢查與推播；可選用模型判斷「有沒有實質進展」 |
| `xharness/tools/jobs.py`、`subagent.py`（改） | 背景工作做完主動叫醒對話；並行槽位保留一格給人的訊息 |
| `xharness/web.py`（改） | 新增「工單」頁；設定頁照設定順序軸排；資安檢查頁加常駐代理的檢查項 |
| `scripts/report/build_usage_report.py`（改） | 使用報告加一章：收到多少事件、准入多少、接了幾張工單、多少要人介入、平均完成時間 |

### 網頁

**工單頁**只先列出要人處理的事：等人回答、待驗收、卡住或失敗、寫回待核准。都沒有時不佔版面。每則事件都能點開看去向。

**設定**照順序軸排，每一步的狀態由實際資料算出：
1. 接來源：GitHub 存放庫與權杖、Telegram 群組
2. 設名單：誰可以叫代理做事
3. 寫規則：代理可以主動做哪些事，例如「預設分支 CI 失敗時重現並提出修正」
4. 觀察一週：observe 模式，核對「本來會接」的紀錄
5. 開自動：切到 auto，寫回仍過核准
6. 維運：Watchdog 通知對象、暫停開關

規則與提示詞每次存檔留版本與歷史。

## 7. 資安

- **事件內容一律當資料**：群組訊息、PR 留言、CI 輸出都可能夾帶提示注入。授權只看准入結果與工單上寫死的授權，訊息內容改不了。
- **對外寫入預設每筆核准**：auto 模式只放寬「接單」，不放寬「寫入」；寫入要另外設定才能放寬。
- **工作代理拿不到 GitHub 權杖**：寫回由管道代辦，避開文章說的「憑證進入模型上下文」。
- **權杖照 `secret-handling` 處理**：用 `_FILE` 或沿用 `channels.json` 的 AES-256-GCM 加密存放；只走 Authorization 標頭；錯誤訊息過遮罩。權限只開單一存放庫的 issues、pull requests、contents。
- **名單用帳號 ID 比對**：用來源給的帳號 ID，不用顯示名稱，防止改名冒充。
- **威脅模型與測試**：`docs/ssdlc.zh.md` 增寫一節，涵蓋事件注入、冒名、權杖外洩；`test/security/` 補跨工單存取測試。

## 8. 實測（在 .70，用 granite）

照文章第 7 節的做法自己量一次，數字寫進 `evals/RESULTS.md`：

1. **消融**：合成約 300 則訊息，其中約 20 則是工作請求，其餘是閒聊、跟進、叫停、CI 訊息。比較三種做法：常駐代理、常駐代理但不直通、單一對話加子代理。每種跑 5 次，量任務完成時間的 P50／P95 與 token。
2. **批次**：主會話接真模型、工作代理用假模型，觸發速率由每分鐘 1 則拉到 40 則，量每批的大小與每個決定平均花的時間。
3. **端到端**：
   - 在測試存放庫開 issue 點名代理，代理回「收到」，然後開出 PR。
   - 有人在 PR 留言要求修改，代理不經主會話直接接著改。
   - 重啟節點後，進行中的工單照常接續，不會重複留言。
   - 全程每筆寫入都在手機核准。

pytest、bandit、`check-compliance.sh --level 中`、`audit-secrets.sh` 全部通過才算完成。

## 9. 分段（一次交付 1.19.0，內部依序做）

| 段 | 內容 | 這段做完怎麼驗 |
|---|---|---|
| 1 | 資料層、來源介面、GitHub 來源 | 重啟後不重播；同一事件只產生一筆觸發 |
| 2 | 准入、主會話、批次、observe 模式、去向紀錄 | 合成訊息跑一輪，每一則的去向都查得到 |
| 3 | 工單、派工、訂閱直通、工作代理工具、outbox、GitHub 寫回與核准 | 端到端從 issue 到 PR |
| 4 | Telegram 群組來源與回覆、跨管道接續 | 群組裡開的工作，到 PR 留言還能接著做 |
| 5 | 重啟復原、Watchdog、背景工作叫醒、保留槽位、工單頁、設定順序軸、使用報告、威脅模型 | 故意讓一張工單卡住，手機收到通知；重啟後不重複留言 |
| 6 | 三項實測、文件、CHANGELOG | 數字寫進 `evals/RESULTS.md` |

分支從 `feat/multiagent`（PR #3）切出；PR #3 合併後，再 rebase 到 main。

## 10. 要先決定的事

1. **先接哪些來源**：建議 GitHub 與 Telegram 群組。學校常用的 Gitea、GitLab 和 Email 放下一版。
2. **代理的 GitHub 身分**：需要一個專用帳號（例如 `xcloud-agent`），以及只限單一存放庫的權杖。帳號要由你建立。
3. **先拿哪個存放庫試**：建議另開一個測試用存放庫，等穩了再用在 xHarness 自己身上。
4. **寫回的預設**：建議每筆都要手機核准；或是在 auto 模式下，讓已接下的工作直接留言。
